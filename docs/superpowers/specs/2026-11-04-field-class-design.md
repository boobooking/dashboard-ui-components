# Проп fieldClass у FormInput и FormTextarea

Дата: 2026-11-04

## 1. Цель и рамки

Приложению нужно менять вид самого поля — например, моноширинный шрифт у
списка ключей в certificates. Сейчас способа нет: `class` со страницы ложится
на корень компонента, ни подпись, ни поле своего семейства шрифта не задают и
наследуют его от корня, поэтому `font-mono` на корне меняет и подпись. Пакет
задаёт общий вид, а детали поля меняет приложение — одним крючком, а не
отдельным пропом под каждую деталь.

В рамках задачи:

- проп `fieldClass` у `FormInput` и `FormTextarea`;
- исключение в тесте-стороже классов;
- тесты, Playground, README.

Вне рамок:

- такой же проп у других полей пакета (`SelectSingleForm`, `AmountForm` и
  других);
- перевод certificates на `FormTextarea` с `field-class="font-mono"`;
- выпуск: версия, тег и публикация — по слову владельца.

## 2. Что показало исследование

- `FormInput.vue` и `FormTextarea.vue`: `inheritAttrs: false`; `class` и
  `style` — на корень (`:class="$attrs.class"`), остальные атрибуты — на
  `<input>` / `<textarea>` (методы `inputAttrs()` / `textareaAttrs()` убирают
  `class`, `style`, `id`).
- Ресет пакета задаёт `<input>` и `<textarea>` `font: inherit` в слое
  `components`; утилиты приложения стоят в слое `utilities` и CSS приложения
  подключается после CSS пакета, поэтому утилита приложения на поле сильнее и
  ресета, и утилит пакета с тем же свойством.
- `tests/utilityPrefix.test.js` разбирает `:class` и падает на
  `Identifier`, кроме `panelClass` в `PopoverPanel.vue`; `$attrs.class`
  пропускает как классы приложения без префикса.
- Публичных пропов с классами для частей компонента в пакете пока нет.

## 3. Решения и их источники

| Решение | Источник |
| --- | --- |
| Не отдельный проп под каждую деталь, а крючок: приложение задаёт стиль поля само | владелец |
| Подпись — стиль пакета, крючок её не задевает | владелец |
| Крючок сразу у `FormInput` и `FormTextarea` | владелец |
| Имя `fieldClass`, значение как у `class` во Vue: строка, массив, объект | автор, показано владельцу |
| `class` на корне — раскладка блока; вид поля — `fieldClass` | автор, показано владельцу |
| Классы приложения через `fieldClass` могут перекрыть и общий вид поля (рамку `field-frame`, отступы) — это решение приложения | автор, показано владельцу |
| Исключение сторожа: `fieldClass` в `FormInput.vue` и `FormTextarea.vue` | автор |
| Ветка `feat/field-class` от `main` | автор |

## 4. API

| Проп | Тип | По умолчанию | Описание |
| --- | --- | --- | --- |
| `fieldClass` | `String`, `Array`, `Object` | `null` | Классы приложения для самого поля (`<input>` / `<textarea>`) |

```vue
<form-textarea v-model="keys" label="Ключи" field-class="font-mono" :rows="16" />
<form-input v-model="code" label="Код" :field-class="{ 'tracking-widest': isCode }" />
```

- Классы ложатся только на `<input>` / `<textarea>` вместе с классами пакета;
  подпись, точка, описание и счётчик их не получают.
- `null`, пустая строка, пустой массив или объект — как без пропа.
- Классы пишутся без префикса `bb:`: это утилиты приложения.
- Значение другого типа (число, `true`) — в режиме разработки предупреждение
  Vue о типе (в production Vue их не выдаёт), поле
  рисуется без классов приложения, компонент не падает.
- `class` и `style` по-прежнему ложатся на корень.

## 5. Тесты

**Vitest**, в `tests/FormInput.test.js` и `tests/FormTextarea.test.js`, табличные:

- строка, массив, объект — классы на поле, классы пакета на месте
  (`bb:field-frame` и др.);
- корень, подпись, описание (и счётчик у `FormTextarea`) классов не получают;
- `null` и пустые значения — на поле только классы пакета;
- смена `fieldClass` после монтирования — классы поля обновляются;
- `class` со страницы — на корне, не на поле;
- значение другого типа — предупреждение, без ошибок.

`tests/utilityPrefix.test.js`: исключение для `Identifier` `fieldClass` в
`FormInput.vue` и `FormTextarea.vue` с комментарием (классы приложения, как
`$attrs.class`), и тест, что в другом файле `:class="fieldClass"` по-прежнему
отклоняется.

**Playwright**, обе страницы, Chromium и WebKit: в разделе `FormTextarea`
поле с `field-class="font-mono"` — у `<textarea>` моноширинное семейство
шрифта, у подписи то же семейство, что у соседнего поля без `fieldClass`.
Тот же сценарий на странице приложения проверяет, что утилита приложения
сильнее ресета пакета. Для страницы без Tailwind (голой) — класс со своим
правилом в `playground/bare.css` (например, `.demo-mono { font-family:
monospace }`), если `font-mono` там не собирается.
